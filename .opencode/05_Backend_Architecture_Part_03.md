# 05_Backend_Architecture.md ## Part 3 — Solution Structure, Vertical Slices & Persistence --- # 35. Solution Philosophy The CallPilot Server is designed for long-term open-source development. The architecture should optimize for: - Feature discoverability - Independent development - Testability - Low coupling - Contributor onboarding - AI-assisted development - Future scalability The codebase should be organized around **features**, not technical layers. A developer working on "Knowledge Upload" should be able to understand that feature by opening a single folder. --- # 36. Architectural Style The server uses a hybrid architecture: - Vertical Slice Architecture - CQRS - DDD Lite - Event-Driven Architecture - Clean boundaries This is intentionally not traditional Clean Architecture. Traditional layered architectures often become difficult to navigate as AI products grow. Vertical slices keep related code together. --- # 37. Solution Structure ``` src/ │ ├── CallPilot.Server.Api ├── CallPilot.Server.Application ├── CallPilot.Server.Domain ├── CallPilot.Server.Infrastructure ├── CallPilot.Server.Shared └── CallPilot.Server.Tests ``` Responsibilities Api HTTP endpoints and WebSocket hubs. Application Commands, queries, workflows, and feature slices. Domain Core business models and domain events. Infrastructure Database, external services, storage, and provider integrations. Shared Cross-cutting abstractions. Tests Unit, integration, and end-to-end tests. --- # 38. Feature-First Organization Inside the Application project, features are grouped by business capability. ``` Application/ │ ├── Meetings/ ├── Knowledge/ ├── Providers/ ├── Authentication/ ├── Dashboard/ ├── Diagnostics/ └── Workflows/ ``` Each feature owns its complete implementation. --- # 39. Example Feature Slice Example: `Knowledge/Upload` ``` Knowledge/ └── Upload/ ├── UploadKnowledgeCommand.cs ├── UploadKnowledgeValidator.cs ├── UploadKnowledgeHandler.cs ├── UploadKnowledgeEndpoint.cs ├── UploadKnowledgeResult.cs └── UploadKnowledgeTests.cs ``` Everything related to the feature lives together. A contributor should not need to search the entire solution. --- # 40. Meetings Feature The Meetings feature is expected to become the largest feature area. ``` Meetings/ ├── StartMeeting/ ├── EndMeeting/ ├── ConnectDesktopAgent/ ├── DisconnectDesktopAgent/ ├── UpdateTranscript/ ├── PublishRecommendation/ ├── GetMeeting/ ├── GetTranscript/ └── GetRecommendations/ ``` Each operation remains isolated. --- # 41. Commands Commands represent intent. Examples ``` StartMeetingCommand EndMeetingCommand UploadKnowledgeCommand ConfigureProviderCommand PublishRecommendationCommand ``` Rules - Commands change state. - Commands should be idempotent where practical. - Commands should emit domain events. - Commands should be validated before execution. --- # 42. Queries Queries return data. Examples ``` GetMeetingQuery GetTranscriptQuery GetRecommendationsQuery GetProviderConfigurationQuery ``` Rules - Queries never modify state. - Queries should be optimized for reading. - Queries may use projections or read models. --- # 43. Workflows Some operations span multiple steps and external systems. These become workflows. Examples ``` StartMeetingWorkflow UploadKnowledgeWorkflow InitializeAISessionWorkflow EndMeetingWorkflow ``` Workflows coordinate commands and external calls while preserving reliability and observability. --- # 44. Domain Layer The Domain project contains the core business model. Examples ``` Meeting MeetingContext Recommendation KnowledgeDocument ProviderConfiguration TranscriptSegment DomainEvent ``` Domain objects should contain business rules but remain free of infrastructure concerns. --- # 45. Domain Events Domain events represent facts. Examples ``` MeetingStarted DesktopAgentConnected TranscriptUpdated CompetitorDetected KnowledgeUploaded RecommendationGenerated MeetingEnded ``` Events are immutable. Events should not contain behavior. --- # 46. Infrastructure Layer Infrastructure contains all external integrations. Examples ``` PostgreSQL File Storage pgvector AI Engine Client JWT Encryption Serilog WebSocket Infrastructure ``` Application code should depend on abstractions, not concrete implementations. --- # 47. Persistence Strategy PostgreSQL is the primary database. The server stores: - Users - Meetings - Transcript segments - Recommendations - Knowledge documents - Provider configurations - Domain events - Diagnostics - Embeddings (pgvector) The AI Engine does not access PostgreSQL directly. --- # 48. pgvector Usage Embeddings are stored alongside application data. Advantages - Single database - Simpler backups - Simpler deployment - ACID transactions - Lower operational complexity This is the default architecture for Phase 1. --- # 49. Read Models Some queries require optimized projections. Examples ``` MeetingSummaryView ActiveMeetingView RecommendationTimelineView KnowledgeSearchView ``` Read models may be denormalized for performance. --- # 50. Transactions Business operations that modify related entities should execute within a transaction. Examples - Start Meeting - End Meeting - Upload Knowledge - Configure Provider Long-running AI operations should not hold database transactions open. --- # 51. File Storage Uploaded documents should be stored separately from PostgreSQL. The database stores metadata and indexing information. Storage implementations should be replaceable. Future options may include: - Local disk - S3-compatible storage - Azure Blob Storage - MinIO --- # 52. API Design The server should expose: - REST endpoints for management operations - WebSockets/SignalR for live meeting updates REST handles: - Authentication - Knowledge uploads - Provider configuration - Meeting management WebSockets handle: - Live transcript - Recommendations - Meeting events - Diagnostics --- # 53. Versioning Public APIs should be versioned from the beginning. Example ``` /api/v1/meetings /api/v1/knowledge /api/v1/providers ``` Versioning protects future evolution. --- # 54. Testing Strategy Every feature slice should contain: - Validator tests - Handler tests - Workflow tests - Integration tests The architecture should make isolated feature testing straightforward. --- # 55. Contributor Experience A new contributor should be able to: 1. Pick a feature folder. 2. Read one command. 3. Read one handler. 4. Run one test. 5. Submit a PR. Low-friction contribution is a primary architectural goal. --- # 56. Engineering Principles The server should remain: - Feature-oriented - Event-driven - Testable - Observable - Modular - AI-provider agnostic - Open-source friendly If a feature requires modifying many unrelated folders, the architecture should be reconsidered. --- End of Part 3
